---
title: Capability cheat sheet
description: Every capability on one page, with its kind, admitted subjects, failure code and refusal codes, generated from the registry and the reference.
---

One row per capability in the engine's registry, generated at build time from `registry.rs` and from each capability's reference section, so the sheet and the sections cannot disagree. Each name links to its section and is spelt for the language you are reading: the registry name in TypeScript, the snake_case method in Python.

<MatcherReference variant="cheat-sheet" />

**Kind.** An assertion answers passed, failed or refused under either polarity. A query reports what it measured and takes positive polarity only. A contract takes no arguments: its requirement is fixed by name.

**Mesh, STEP, glTF.** Yes when the section's admitted geometry lists that subject class. Mesh is a `mesh-buffer-v1` subject; glTF covers glTF and GLB. `toSatisfyRationalPlate` (Python `to_satisfy_rational_plate`) admits a `rational-plate` subject only.

**Failed with.** The code a failed claim carries; `none` means the section names no failure code.

**Refused with.** The section's own refusal codes. The [common refusals](/docs/reference/overview#common-refusals) apply to every row: `MATCHER_TIMEOUT` when the budget is spent, `GEOSPEC_ANALYSIS_LIMIT` and `GEOSPEC_RESOURCE_LIMIT` when an analysis or admission limit is exceeded, `GEOSPEC_EVIDENCE_UNSUPPORTED` on a face-reading claim over a STEP whose faces carry no surface, `GEOSPEC_UNSUPPORTED_EVIDENCE` on a y-up STEP, and `GEOSPEC_BACKEND_FAILED`. [Read a refusal](/docs/guides/read-a-refusal) says what to change.
