One Rust engine ships three ways. All three take the same request bytes and return results from the same engine source, so the choice is about the host, not the answers.

| Host                                       | Import                | Notes                                               |
| ------------------------------------------ | --------------------- | --------------------------------------------------- |
| Node 24+ on macOS arm64 or Linux x64 glibc | `geospec-engine/node` | Native addon from the prebuild; no `initialize`     |
| Node 24+ elsewhere                         | `geospec-engine`      | WASM; call `initialize()` first                     |
| Chromium, Firefox, WebKit                  | `geospec-engine`      | WASM; serve or bundle the `.wasm` file              |
| CPython 3.13 and 3.14                      | `geospec`             | Wheel from PyPI, with `load_model` and `expect_geo` |

## Node

```ts
import { Engine } from 'geospec-engine/node';

const engine = new Engine(); // the native addon needs no initialize()
```

The native constructor also accepts a filesystem cache location and a count of execution permits, which includes the calling thread and cannot exceed the host's available parallelism. Where no prebuild matches the host, the import throws `Cannot find native binding` and never falls back; [Install](/docs/install#what-gets-installed) lists the two prebuilds.

## Browsers

```ts
import { Engine, initialize } from 'geospec-engine';

await initialize(); // or initialize(bytesOrUrl) to load the module from elsewhere
const engine = new Engine();
```

`geospec-engine/wasm-binary` resolves to the `.wasm` file itself, for a bundler or a server that hosts it. The same import runs on every Node host, so a script that must run anywhere takes this entry.

## Python

The wheel installs two packages. `geospec_engine_native` is the extension: an `Engine` with the same operations in snake_case over `bytes`. `geospec` is the authoring API over it: `GeoSpecEngine` owns the native engine and, as a context manager, binds `load_model` to a model root. The same volume claim as the demo:

```python title="binding.py"
from geospec import GeoSpecEngine, expect_geo, load_model

with GeoSpecEngine(model_root="."):
    box = load_model(file="box-10x20x30.step", format="step")
    report = expect_geo(box, claim_id="volume").to_have_volume(value=6000)
    print(report.result["claimId"], report.result["status"], report.result["evidence"]["measured"])
```

```console
volume passed 6000
```

`expect_geo` returns a `GeoSpecAssertionReport` on a pass, with `.result` and the canonical plan and result bytes, and raises `GeoSpecAssertionError` on a failed or a refused claim. `evaluate_geo` returns the report without raising. Under pytest the plugin makes an engine per test, so a test calls `load_model` without a context manager.

## Variations

**A build that must run on every Node host.** Import `geospec-engine` and call `initialize()`. The WASM module is about 16 MB and compiles once per process; the native addon skips that cost where a prebuild exists.

**One script, either binding.** Import `geospec-engine/node` inside a `try` and fall back to `geospec-engine` when it throws, and record which one ran. The two return the same result bytes for the same request, so the choice changes speed, not verdicts.

**A Linux arm64 or Windows host.** No prebuild exists, so Node runs the WASM module and Python has no wheel. [Install](/docs/install#installing-for-another-platform) covers building an image for another platform.

**Raw bytes from Python.** `geospec_engine_native.Engine` exposes `ingest_subject`, `process_request` and `evaluate_claim` over `bytes` for a host that builds its own requests. [Reproduce a result](/docs/guides/reproduce-a-result) shows what to keep from either side.
