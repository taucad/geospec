---
title: Set tolerances and budgets
description: State how close a measurement must come, compare with strict bounds, and set the work a claim may spend before it is refused.
---

Every claim carries two limits: a `tolerance` inside its expectation, which says how close the measurement must come, and a work budget, which says how much work the engine may spend deciding it. Both are recorded in the result, so two readers of one result see the same rule.

## Tolerance

A value matches when `abs(measured - expected) <= tolerance`. The default is 0.02 mm; `tolerance: 0` demands the nominal value, which a STEP solid meets and a tessellated mesh rarely does. One tolerance covers every value in the expectation: each axis of a bounding box, the diameter of a hole, a volume. The result keeps the expectation with its tolerance filled in as `evidence.normalizedExpected`.

A negative tolerance, or a bounding-box expectation with a tolerance and no bound, is rejected before anything is measured: TypeScript throws a `ProtocolError` whose `code` is `invalid-claim`, and Python raises `GeoSpecAssertionError` with `code == "invalid-claim"` and no report.

## Work budgets

The engine charges work units as it measures, before it reads any cache, so a claim costs the same on every host and every run and never depends on wall time. A claim that spends its budget is refused with `MATCHER_TIMEOUT`: the diagnostic's `details` name the matcher, the budget and the units used, and the claim was not decided. The default budget is 8,000,000 units.

<TypeScript>

`workUnitLimit` sets the budget per chain, `expectGeo(part, { workUnitLimit: 100 })`, per loaded model, `loadModel({ source, format, workUnitLimit })`, or per assertion client. A limit of 0, or above this host's maximum of 512,000,000, throws a `TypeError` before anything runs. Beside the engine's `budget` and `unitsUsed`, the details carry `limit`, `used` and `maximumLimit`.

</TypeScript>

<Python>

The budget belongs to the engine: `GeoSpecEngine(model_root=".", work_unit_budget=100)` applies it to every claim the engine evaluates, and `work_unit_budget=0` raises `ValueError`. The details carry `budget`, `matcher`, `unit` and `unitsUsed`.

</Python>

The gear is a mesh of 624 triangles, and a bounding box over a mesh charges per triangle: 3,744 units for this one. The spec below allows 100, so the claim is refused before it measures anything.

<SpecDemo subject="gear">

```ts
expectGeo(part, { workUnitLimit: 100 }).toHaveBoundingBox({ size: { z: 5 } });
```

</SpecDemo>

Raise the limit to 10000, `workUnitLimit: 10000` here or `work_unit_budget=10000` on the engine, and the claim passes. Then add `tolerance: 0` beside `size` and it fails with `GEOSPEC_BOUNDING_BOX_MISMATCH`: the triangles span 4.999976634979248 mm, not 5.

## Strict comparisons

Where a matcher takes a numeric expectation, write a number, or an object with any of `value`, `greaterThan`, `greaterThanOrEqual`, `lessThan` and `lessThanOrEqual`. The tolerance applies to `value` only; the four comparisons are strict as written. The plate's volume is 30429.20367320504 mm³, so the first claim below passes and the second fails with `GEOSPEC_MEASUREMENT_MISMATCH`, although its bound is within 0.02 of the measurement: no tolerance widens a comparison. An object with none of the five fields is an `invalid-claim` error.

<SpecDemo subject="plate">

```ts
expectGeo(part).toHaveVolume({ value: { greaterThan: 30000, lessThan: 31000 } });
expectGeo(part).toHaveVolume({ value: { greaterThan: 30429.21 } });
```

</SpecDemo>

## Never widen a tolerance to pass

A failed claim reports what it measured. Read the measurement, then fix the model or correct the expectation to the value the design states. Widening `tolerance` until the claim passes records a looser requirement than the design has, and the next part that drifts inside the wider band passes too; the engine's own suggestions end with `preserve the authored tolerance.` A refusal is not a reason to widen anything either: [Read a refusal](/docs/guides/read-a-refusal) says what to change instead.

## Variations

**A tolerance with its own name.** `toHaveConnectedComponents` takes `toleranceMm`, the gap below which two pieces count as one; it defaults to 0.02 mm and the result records it under that name. [Check meshes](/docs/guides/check-meshes) covers it.

**What a claim costs.** Bounds, closure, volume and mesh integrity on the gear each charge 3,744 units, a component count 49,005 and an `inspectGeometry` axis selector 52,138. A hole claim on the STEP plate charges 3, and the plate's bounds and volume pass with a budget of 1. Read what a refused claim spent from `unitsUsed` in its details.

**Budgets on queries.** A query charges the same way: `client.query` spends the client's `workUnitLimit`, `query_geo` the engine's budget, and `analyzeMesh` on the gear refuses at a budget of 1 with `MATCHER_TIMEOUT`. [Query geometry](/docs/guides/query-geometry) covers the queries; the [matcher reference](/docs/reference/overview#common-refusals) lists the refusals every matcher shares.
